## 一、交付物

一个独立应用 `apps/trace`（端口 4316）、五个调查能力插件、一个元宝搜索服务端适配器，以及一条真实跑通的调查闭环：
**立案 → 事实与检索式确认 → 多轮真实检索与原文取证 → 证据核验与保守结论 → 人工确认 → 调查档案导出**。

| 能力 | 作用 | 复用的公共部分 |
|---|---|---|
| `trace.case.intake` | 规范化问题、待核查说法、人工确认的事实与检索式 | 上传契约 + 证据表 |
| `trace.facts.confirm` | 校验/合并检索式，冻结检索预算与检索配置快照 | 证据表 |
| `trace.web.search` | 调元宝搜索 SearchPro，逐条记录请求，抓取原文正文 | 证据表、步骤超时与取消 |
| `trace.evidence.verify` | 同源转载合并、支持/反对判定、保守结论 | 证据表 |
| `human.confirm`（既有） | 人工确认节点，审批绑定输入摘要 | 完全复用，未改写 |
| `trace.archive.export` | 生成可下载的 `调查档案.md` / `.json` | 审批范围、SHA-256 文件写入、最终凭证 |

公共运行时只做两处最小适配（无框架重构）：
1. `uploadSchema` / `UploadInput` 增加可选 `payload`（结构化案件）与 `dataConsent`（外发检索授权）；
2. `engine.createRun` 的外发授权判定区分「发往模型」（`modelConsent`）与「发往外部检索服务」（`dataConsent`）。

`/v1/catalog` 增加 `tencent-wsa-search` provider，前端只读可用性，永远拿不到密钥。

## 二、元宝搜索接入（官方契约）

来源：`cloud.tencent.com.cn/document/product/1806/130615`（服务 API KEY 方式）、`121799`（购买方式）、`121804`（常见问题）。

- `POST https://api.wsa.cloud.tencent.com/SearchPro`，`Authorization: Bearer sk-...`，请求体 `{"Query":"..."}`。
- 响应 `{"Response":{"Pages":[...],"Query":"...","RequestId":"..."}}`，**`Pages` 每一项都是被二次序列化的 JSON 字符串**（`passage/score/date/title/url/site/images/favicon`）。适配器做第二次 `JSON.parse`，解析失败条目计入 malformed，不丢弃整次响应。
- 错误码映射：`UnauthorizedOperation → SEARCH_UNAUTHORIZED`、`ResourceNotFound → SEARCH_NOT_OPENED`、`ResourceUnavailable → SEARCH_QUOTA_UNAVAILABLE`、`RequestLimitExceeded → SEARCH_RATE_LIMITED`（指数退避重试）、`InternalError → SEARCH_PROVIDER_ERROR`；另有 `SEARCH_TIMEOUT`、`SEARCH_NETWORK_ERROR`、`SEARCH_RESPONSE_INVALID`。
- 密钥只从进程环境读取（`PLATFORM_WSA_API_KEY`），不写日志、不回传前端、不落盘。
- 官方口径：QPS 20（极速版/标准版）、平均时延 600–800ms、P99 约 1200ms、**不含微信公众号内容**。适配器默认串行检索留 350ms 间隔，产品不承诺覆盖公众号。

### 邀请码福利与额度的实际关系（不自行假定）

官方「购买方式」「常见问题」均未记载邀请码福利与账户额度的换算或叠加关系，因此：代码与界面**不假设**任何邀请码已领取或已生效；唯一判据是接口真实返回（未开通 → `SEARCH_NOT_OPENED`，欠费/额度不足 → `SEARCH_QUOTA_UNAVAILABLE`）；服务状态与资源包余量需人工在控制台确认。

### 真实运行暴露并已修复的四个判定缺陷

首轮真实数据把问题暴露得很清楚，全部已修并加了回归测试：

1. **年份被当成数值证据**：来源只要出现「2025年」就被判「数量断言一致」。改为年份/月/日不参与数量比对。
2. **数值分歧冒充反证**：事实没有数量断言时，来源里的「1150公里、10座加氢站」被判为反证，凭空造出「存在争议」。改为只有事实本身含同单位数量断言时才做数量比对。
3. **期间型时间要求被当成发布时间**：事实「2024年产量」，2025 年 1 月发布的统计公报被判「范围外」，14 条官方来源全部作废。改为：期间型看内容是否涉及该期间，时效型（最近一年/现行）才看发布时间。
4. **比较语义缺失**：「超过1200万辆」遇到 1288.8万辆被判反证。改为解析比较方向（超过/以上/至少/低于/不超过），同单位下不违背即支持；比较式支持还要求命中同一表述片段，避免用「汽车总产销 3140万辆」冒充新能源产量证据。

另修两个运行期问题：`PLATFORM_DATA_DIR` 保留模板占位值（`/absolute/...`）时 Runtime 曾直接抛 `ENOENT '/absolute'`，现在改为打印提示并回退到默认数据目录（可正常启动）；`/v1/receipt` 原先写死 `report.export`，业务自有导出拿不到最终凭证，改为按「已完成且声明 `local_file` 副作用」识别导出步骤。

## 三之二、产品完善轮（体验与追问）

在已跑通的闭环上补齐真实可用的交互，不重建框架：

- **入口**：一个问题输入框 + 「要核查的说法」+ 三张真实案例卡（点一下带入）；明确写出调查范围、你会拿到什么、谁下结论。检索计划默认折叠，普通用户不必看 CAP/Runtime 字段。
- **过程页**：横向阶段进度；每条事实一张卡，先给支持/反对/无法确认/无关四类计数与独立来源数，再把证据按关系排序列出；每条证据带原始网页入口与「关键原文摘录」（取到正文用正文，未取到用搜索摘要）；同源转载标注「与某站为同一原始内容，按 1 条独立证据计算」。
- **证据追问（本轮新增能力）**：任意事实或任意一条证据都可以「继续追问」→ 换检索式 → 真的再查一次元宝搜索 → 结果并入同一条调查 → 用同一套规则重算结论。新增端点：`POST /v1/runs/:id/trace/followup`、`POST /v1/runs/:id/trace/reassess`、`GET /v1/runs/:id/trace/assessment`（实现见 `services/runtime/src/trace-followup.ts`，检索/抓取/判定全部复用既有适配器，不伪造执行）。
- **档案页改为结论优先**：结论类型 → 结论句 → 最关键支持依据（按是否取得原文排序）→ 来源矛盾 → 尚未解决的问题（系统明确写出还缺什么）→ 来源清单（按同源分组）→ 下载档案与凭证；技术细节收进最底部折叠区。
- **四态关系**：规则新增「无关」（relevance < 12%），与「无法确认」区分，避免把检索命中的无关网页混进证据里。

真实数据验证：C 案例（证据不足）追加一次检索后独立来源从 15 增至 20、网页 20、追问 1 次，结论仍为「证据不足」并保留具体缺口——追加检索不会为了让结论好看而放松判定。

## 三之三、版本一致性与人工修正（本轮新增）

已交付的档案不允许被后续追问悄悄改写。做法是「版本即证据」，不另建版本平台：

- **版本记录**：每次交付写一条 `trace.revision` 证据（版本号、时间、确认人、真实产物 id/字节/SHA-256、当版评估快照、当版变化说明）。首版由导出插件写入；改版前的历史 run 没有这条证据，读取时用现有产物合成第 1 版并标注 `derived`，历史调查不会因此没有版本可看。
- **只增不改**：第 N 版文件名为 `调查档案-vN.md/.json`，写新文件、不动旧文件与旧 artifact 行。旧下载链接永远指向旧版本（实测：C 案例 v1 的 SHA-256 `dd95da0a…` 在 v2 生成后下载仍完全一致）。
- **为什么变化**：`GET /v1/runs/:id/trace/revisions` 用「上次交付的评估快照 vs 当前重算结果」生成变化说明（结论变化、独立来源增减、原文增减、逐条事实判断与独立来源数变化、新增追问/修正条数），同一份文案写进档案的「本版变化」与页面的变化列表。
- **人工修正**：`POST /v1/runs/:id/trace/correction`（pageId/factId/relation/note/actor）只记录判断，不改原始搜索返回与摘录；`applyCorrections()` 保留 `autoRelation` 与修正人/原因/时间，并用与自动判定完全相同的 `aggregateCase` 规则重算。档案里每条来源同时写「人工修正」与「系统自动判断」，另有独立的「人工修正记录」一节。
- **修正的影响**：每次修正写入时同时记录「采纳这条修正前后」的真实重算差异（来源关系、事实判断、支持来源数、独立来源数、结论类型），页面上直接写「对结论的影响」，不让读者自己推。老记录用 `npx tsx tooling/trace-correction-backfill.ts` 按同一顺序重放补算。
- **重新确认**：`POST /v1/runs/:id/trace/redeliver` 要求存在未确认的追问或修正，写新版本文件 + 版本证据；没有变化时明确拒绝（`NO_CHANGES`），不会凭空造版本。
- **档案渲染单一来源**：`services/runtime/adapters/trace/archive.ts` 的 `renderArchive()` 同时服务首版插件与改版端点，避免两套口径；结论句由 `buildStatement()` 统一生成。
- **证据不足依旧保留**：C 案例经过 1 次真实追问 + 2 次人工修正、生成到第 3 版，结论始终是「证据不足」，缺口列表照旧显示。

界面：调查过程页显示「已交付第 N 版 / 当前结论有新变化待确认」+ 变化列表 + 确认人输入 + 「重新确认，生成第 N+1 版」；每条证据可「修正这条判断」（四态选择 + 原因 + 保存即重算）；档案页有版本切换（含「当前结论」未成档态）、按版本下载、本版变化说明、人工修正记录。实测：390×844 与 1440×900 三页均无横向溢出、无控制台报错。

## 三之五、来源独立性：三态判定（本轮修正）

问题：三个案例 16/14/20 条来源在旧口径下**一条都没合并**，等于把不同域名默认为独立证据。

排查结论（先查再改，不凭"没触发"就改阈值）：

- B 的两条统计局链接是同一篇文章（同文章编号 `t20250228_1958819`，只是挂在 `/sj/sjjd/` 与 `/zwfwck/sjfb/` 两个栏目）；另有两条中国政府网链接是同一篇的繁体镜像（`big5.www.gov.cn/gate/big5/...`）。旧口径既不看文章编号也不还原镜像地址，所以没合并。
- C 有 3 条同标题（人民政协网／人民网／今日头条「我国首条跨区域氢能重卡干线投运」）、2 条摘要高度相似（腾讯新闻与今日头条「1150 公里」），旧口径只看 `passage+title` 的 24 字分片 Jaccard ≥0.55，摘要是改写过的短句，达不到。
- A 有 1 条摘要与另一条逐字一致（泾县政府），其余 6 条都是「全文／主席令」类页面，标题相近但都取不到正文。

改法（不降阈值，改用可指认的依据）：`groupSources()` 只在下列证据成立时合并，并写明依据：

1. 同一网址（含 `big5/gate/big5`、`m.`、`wap.` 等镜像还原）；
2. **同一发布方（同一主域名）下的同一文章编号**（`t\d{8}_\d+`、`content_\d+`、`/n/1234567.html` 等）——跨站的同编号只是线索，不合并；
3. 搜索摘要逐字一致（≥30 字）或几乎逐字一致（≥0.92）；
4. 两边正文 5 字片段包含度 ≥0.7 或 Jaccard ≥0.55。

其余一律不算"确认同源"。**跨站标题完全一致或近乎一致只作线索**，与"跨站同编号""摘要高度相似""正文部分重合""摘要开头相同"一样标为**独立性未确认**：不并簇、不计入独立证据，页面与档案都写原因。

另外新增"共同原始出处"：若来源正文里明确写出"据某机构发布/公布/统计数据"，且同一机构被两条以上来源引用（如 B 的「中国汽车工业协会」、C 的「国家能源局」），这些报道视为同一原始出处的二次转述，结论里**按 1 条独立证据计**，并在来源卡片与档案里并列显示。

术语也随之改正：状态只有三种——`duplicate`（能指认是同一篇）、`unconfirmed`（有线索但无依据）、`unique`（**未检测到重复**）。"唯一"不等于"已证实独立"，所有界面与档案都不再写"独立性已确认"。

计数口径随之变成三层：**检索网页数 → 独立证据簇数 → 独立性未确认数**；支持结论只认独立证据簇（≥2 簇且至少 1 份原文）。

| 案例 | 检索网页 | 合并（能指认同源） | 独立性未确认 | 未检测到重复 | 支持来源簇 | 结论 |
|---|---|---|---|---|---|---|
| A 个人信息保护法 | 16 | 1 | 6 | **9** | 7 | 仍有依据支持 |
| B 新能源汽车产量 | 14 | 2 | 3 | **9** | 8（2 条同引中汽协按 1 条计） | 仍有依据支持 |
| C 氢能重卡加氢网络 | 20 | 2 | 5 | **13** | 1（2 条同引国家能源局按 1 条计） | 仍证据不足 |

「未检测到重复」只表示没有发现重复，**不代表已经证明独立**；结论只要求"≥2 个未检测到重复且至少 1 份原文"的来源簇。

重算产生的新结论不自动覆盖档案：`reassess` 支持 `force` 重算，`revisions` 把"重算但未成档"也算作待确认变化，`redeliver` 才能出 v2/v3/v4。三份新档案的变化一栏首行写着「按更新后的证据判定规则重算（同源识别更严格）后重新确认」。

## 四、可靠性设计（为什么不会把命中当真相）

- **独立来源**：按网址/文章编号/标题/正文重合四类可指认依据合并（见三之五）；证据不足的标为「独立性未确认」，不并簇、不计入独立证据。同簇只算一条独立证据，界面写明合并依据。
- **原文依据**：支持性来源至少一条要取得原文正文（去标签后的页面文字），否则结论降级为「仅有搜索摘要」→ `insufficient`。
- **数量断言**：只比较同单位数字，并尊重「超过/以上/低于/不超过」的比较方向；比较式支持还要求命中同一表述片段；无法判定时给 `unclear`，绝不冒充反证。
- **时效**：区分「事实所指期间」（看内容是否涉及）与「时效要求」（看发布时间），不把次年发布的统计公报当成过期。
- **主体/地区**：`subjectScope` 未在来源中出现时显式记录「适用性存疑」。
- **矛盾**：明确否定表述（不是/并非/不实/辟谣…）或同单位数量违背比较关系才判反对；同时存在支持与反对 → `disputed`，不单方面下结论。
- **结论类型**只有五种：有依据支持 / 存在反证 / 存在争议 / 信息过期或原文不足 / 证据不足；每种都带理由。
- **原文抓取安全**：仅 http/https，DNS 解析后拒绝环回/私有网段/链路本地地址，手动跟随重定向并逐跳校验，限制字节数与时长。
